فروشگاه فارسی محصولات پلاستیکی با Next.js (App Router) و backend مبتنی بر Node.js و Express. مشتری محصول را به سبد اضافه می‌کند، با شماره موبایل وارد می‌شود، آدرس تحویل می‌دهد، سفارش ثبت می‌کند و وضعیت سفارش را از حساب کاربری یا صفحه‌ی پیگیری می‌بیند.

> وضعیت فعلی: **۱۳۴۸ تست خودکار، همه سبز** — ۶۵۷ دود + ۴۷ OWASP + ۴۵ امنیت + ۳۱ تخفیف + ۱۸ یکپارچگیِ گزارشِ بنچمارک + ۱۴ هم‌ترازیِ پنجره‌ی صبر + ۸۷ پنجره‌ی ارسال مجدد + ۲۲ استراتژیِ سرویس‌ورکر + ۵۰ کشِ فشرده‌سازی + ۱۷ دفتر رویدادها + ۵ نگهبانِ پنلِ بازنشسته + ۴۵ بررسیِ راستیِ عددهای README + ۳۱۰ آزمونِ فرانت‌اند (به‌علاوه‌ی سه نگهبانِ بی‌شمارش: مرزِ راز، مرزِ پنج‌تلاشِ کدِ پیامکی، و هارنسِ تخریبیِ خودِ نگهبان‌ها). فرانت‌اند Next.js برابری کامل با Express برای فروشگاه مشتری دارد، صفحه‌ی نتیجه‌ی سفارش خودش وضعیت پرداخت را پیگیری می‌کند، و **هر ۱۳ نمای پنل ادمین** در Next.js است — پنلِ قدیمیِ Express (`frontend/admin.html`) حذف شد و همان مسیر همچنان ۴۰۴ می‌دهد، ولی `/admin` از سمتِ Express به همان پنلِ Next هدایت می‌شود تا لینکِ «پنل مدیریت» در صفحه‌ی حساب به ۴۰۴ نخورد. ورودِ پیامکی هر کد **پنج تلاش** دارد و تا پیش از سوختن، عددِ تلاشِ باقی‌مانده به کاربر گفته می‌شود؛ خودِ سوختن هم یک رویدادِ قرمز در دفترِ پنل می‌گذارد.
>
> عصرِ صفحه‌های `.html` هم تمام شد: هر نامِ `.html` روی همان دامنه با **۳۰۱** به مسیرِ تمیز می‌رود و متنِ همان صفحه‌ها (همان‌طور که Express سرو می‌کرد) در `next-frontend/tests/fixtures/legacy-oracle/` منجمد مانده تا سنجشِ برابری بی‌مرجع نماند.
>
> و خودِ پوشه‌ی `frontend/` هم حذف شد — تنها کپیِ زنده‌اش حالا `next-frontend/tests/fixtures/legacy-src/` است (کپیِ بایت‌به‌بایتِ پیش از حذف، برای نگهبان‌هایی که مرجعِ مقایسه می‌خواهند). نگهبان‌هایی که فایل‌های آن را می‌شمردند بازنشسته شدند و سنجش‌هایی که هنوز درباره‌ی *محصولِ زنده* بودند به Next منتقل شدند؛ فهرستِ تناظر یک‌به‌یک در بخشِ «بازنشستگیِ فروشگاهِ Express» پایین‌تر آمده است.

## وضعیت فنی فعلی

- Node.js `>=22.5`، Express و SQLite داخلی Node — **فقط ۳ وابستگیِ اجرا** (`express`، `express-session`، `dotenv`)
- **Next.js 15.5** با App Router، React 19، TanStack Query 5، Tailwind v4 — آزمونِ فرانت‌اند با Vitest 5 + jsdom
- **۱۵۵ تابع** در `db.js` (۲,۹۷۵ خط) — ۲۶ فایل کتابخانه + ۹ مسیر API + ۵ ابزار مدیریتی
- پنل ادمین: **۱۳ نما از ۱۳** در Next.js — پنلِ Express حذف شد؛ یک‌منبعِ حقیقت در `next-frontend/src/lib/adminSections.ts`
- **بازنشستگیِ نام‌های قدیمی**: هر `.html` عصرِ Express روی همان دامنه ۳۰۱ به مسیرِ تمیز می‌رود (نگاشتِ یکتا در `backend/lib/legacy-redirects.js`)، sitemap و کانونیکال‌ها همان مسیرهای تمیز را می‌گویند، و بازگشتِ درگاهِ پرداخت مستقیم به `/order-success` می‌رسد — بدونِ پرشِ اضافه برای مشتریِ پول‌داده
- **اوراکلِ منجمد**: متنِ ۹ صفحهٔ بازنشسته با کارنامهٔ SHA-256 در `next-frontend/tests/fixtures/legacy-oracle/` و متنِ کاملِ سورسِ عصرِ Express در `next-frontend/tests/fixtures/legacy-src/` نگه داشته شده؛ سنجشِ برابری بدنه را از فایل می‌خواند و کدِ وضعیت را زنده می‌سنجد
- ورود: هر کدِ پیامکی **۵ تلاش** (شمارش روی دیسک، رفرش‌ناپذیر و مشترک بین workers) با نمایشِ تلاشِ باقی‌مانده، و قفلِ پله‌ایِ رمزِ عبور (۱/۵/۱۵/۶۰ دقیقه)
- تست: دود **۶۵۷** | OWASP **۴۷** | امنیت **۴۵** | تخفیف **۳۱** | یکپارچگیِ بنچمارک **۱۸** | هم‌ترازیِ پنجره‌ی صبر **۱۴** | پنجره‌ی ارسال مجدد **۸۷** | استراتژیِ سرویس‌ورکر **۲۲** | کشِ فشرده‌سازی **۵۰** | دفتر رویدادها **۱۷** | پنلِ بازنشسته **۵** | عددهای README **۴۵** | فرانت‌اند (Vitest) **۳۱۰** = **۱۳۴۸**
- بنچمارک: **۱۰,۰۰۰ کاربر همزمان — ۱۰۰٪ موفق، صفر خطا**
- شاخهٔ اصلی: `main` (تنها شاخه — بدون شاخه‌ی جانبی)

## Quick start

نیازمندی: Node.js نسخه‌ی ۲۲.۵ یا بالاتر.

```bash
# اجرای سریع (Windows) — هر دو سرور با هم؛ مرورگر روی فروشگاه باز می‌شود:
StartSite.bat                                  # http://localhost:3001

# یا دستی — دو پنجره:
cd backend
npm install
copy .env.example .env   # Windows
# یا: cp .env.example .env
npm start                                      # :3000 — API، عکس‌ها و پلِ ۳۰۱
```

`StartSite.bat` اول بک‌اند را روی `:3000` بالا می‌آورد (API، عکس‌ها و پلِ ۳۰۱ نام‌های
قدیمی)، بعد اگر بیلدی نباشد یک‌بار `npm run build` می‌زند و بعد فروشگاهِ Next را روی
`:3001` سرو می‌کند — همان چیدمانی که سنجش‌های زنده انتظار دارند. `.env`های محلی را
فقط اگر نباشند می‌سازد (موجود را دست نمی‌زند)، و `SESSION_SECRET` در اجرای محلی
خودکار و موقت ساخته می‌شود.

فروشگاهِ Next یک برنامهٔ جداست و پنجرهٔ خودش را می‌خواهد:

```bash
cd next-frontend
npm install
copy .env.example .env   # Windows (API_ORIGIN و NEXT_PUBLIC_SITE_URL)
npm run build            # با بک‌اندِ زنده — صفحه‌های از پیش رندر‌شده از دیتابیس داده می‌گیرند
npm start                # روی http://localhost:3001
```

Express روی `http://localhost:3000` بالا می‌آید — API، عکس‌های محصول و **پلِ بازنشستگی**: هر نامِ `.html` عصرِ Express با **۳۰۱** به مسیرِ تمیزِ همان صفحه روی همین دامنه می‌رود، پس فروشگاه دیگر از Express سرو نمی‌شود. Next روی `http://localhost:3001` می‌نشیند و این دو به هم گره خورده‌اند: `API_ORIGIN` در `next-frontend/.env` می‌گوید Next داده را از کجا بخواند، و `SITE_URL` در `backend/.env` باید با `NEXT_PUBLIC_SITE_URL` یکی باشد — وگرنه canonical/og:url دو طرف نمی‌خوانند و برابریِ زنده هر صفحه را «واگراییِ تازه» می‌بیند (جزئیات در `HTTPS-GUIDE.md`).

## قابلیت‌های کلیدی

### فروشگاه مشتری (Next.js — برابری کامل با Express)
- صفحه اصلی با محصولات پرفروش، جستجوی زنده، و نوار اطلاعیه
- فهرست محصولات با فیلتر دسته/قیمت/موجودی، مرتب‌سازی و صفحه‌بندی
- صفحه محصول با گالری چندعکسه (lightbox)، مشخصات، نظرات و محصولات مرتبط
- سبد خرید با تخفیف و هزینه ارسال (قابلیت بازگرداندن آیتم حذف‌شده)
- ورود با کد پیامکی (OTP) — ۵ باکس واقعی تکرقمی با cooldown پایدار، مدیریت 429، و «چند تلاش مانده» پیش از سوختنِ کد
- پرداخت از طریق زرین‌پال — و اگر اینترنتِ مشتری وسطِ درگاه قطع شود، صفحه‌ی نتیجه خودش تا ۴۱ دقیقه وضعیت را پیگیری می‌کند
- حساب کاربری با آدرس‌ها، سفارش‌ها و علاقه‌مندی‌ها (۳ تب، با قابلیت لغو سفارش، مرجوعی، فاکتور چاپی)
- پیگیری سفارش بدون ورود (شماره سفارش + موبایل)
- علاقه‌مندی‌ها (heart button، صفحه جداگانه، افزودن به سبد)
- نمایش محصولات اخیراً مشاهده‌شده
- کد تخفیف قابل کپی در بنر پرومو
- جستجوی زنده با پیشنهادات (debounced) و ناوبری با کیبورد

### پنل مدیریت
هر ۱۳ نمای پنل در Next.js است و پنلِ قدیمیِ Express دیگر وجود ندارد. نوارِ ناوبری هنوز همان ترتیبِ نسخه‌ی Express را دارد تا مدیر مجبور نشود جای بخش‌ها را از نو یاد بگیرد.

چارچوبِ فروشگاه در پنل **نیست**: هدرِ فروشگاه (جستجو، سبد، «دسته‌بندی کالا» و نوارِ اعتماد) و پاورقی‌اش با `HideOnStandalone` در هر مسیرِ `/admin*` پنهان می‌شوند — کاری که تا پیش از این فقط برای `/login` انجام می‌شد. به‌جایشان سرِ پنل یک نوارِ چسبان (`sticky`) است: برند و شماره‌ی حساب، یک دکمه‌ی «بازگشت به صفحه سایت»، و زیرش نوارِ بخش‌ها با قرصِ توپُرِ بخشِ جاری. پس راهِ برگشت به فروشگاه بسته نمی‌شود، فقط از کلِ نوارِ خرید به یک دکمه کاهش پیدا می‌کند؛ و در صفحه‌های بلندِ پنل (سفارش‌ها، رویدادها، وضعیت سیستم) هم بخشِ جاری و هم آن دکمه همیشه در دسترس‌اند.

سرصفحه‌ی هر ۱۳ صفحه از یک قالبِ مشترک می‌آید (`components/admin/PageHead.tsx`): کاشیِ آیکون، عنوان، یک‌دو جمله توضیح و یک خطِ موییِ محو. قبل از این، همان `div` و `h1` و `p` سیزده بار تکرار شده بود؛ آیکون و عنوانشان هم از همان `adminSections.ts` خوانده می‌شود، پس نوارِ ناوبری و سرصفحه هیچ‌وقت دو چیزِ متفاوت نمی‌گویند.

دو نمودارِ پنل تا چندی پیش **تخت** بودند: نمودارِ ۱۴ روزِ داشبورد و «درآمد ماهانه»ی CRM ارتفاعشان درصدی بود ولی والدشان ارتفاعِ قطعی نداشت، پس هر میله ۰ پیکسل می‌شد (اندازه‌گیری: ۱۴ میله، همه صفر). حالا هر دو داخلِ یک لایه‌ی `flex-1` با ارتفاعِ قطعی می‌نشینند و میله‌های واقعی می‌کشند.

- **داشبورد** — فروش، سفارش‌های باز، هشدارها و رویدادهای اخیر
- **سفارش‌ها** — تغییر وضعیت، کد رهگیری، یادداشت، لغو و مرجوعی
- **انبار و کالا** — ویرایش سریع قیمت/موجودی، محصول جدید، آپلود عکس، انتشار و برداشتنِ کالا
- **مشتری‌ها** — آمار خرید، جستجو، صفحه‌بندی و نقش کارمند
- **CRM مشتریان** — امتیازدهی RFM، سگمنت‌های هوشمند (VIP/پرخطر/بازگشتی)، تایم‌لاین فعالیت، یادداشت و پیگیری (با فیلتر تگ، حذف یادداشت/تسک)
- **نظرات** — تأیید یا رد دیدگاه خریداران
- **تخفیف‌ها** — کد تخفیف درصدی یا ثابت با سقف و تاریخ انقضا
- **عمده‌فروشی** — صفِ تماسِ درخواست‌های B2B: گذرِ وضعیت (جدید → تماس گرفته شد → انجام شد)، شمارش سنی، حذف دو مرحله‌ای
- **گزارش‌ها** — نمودار فروشِ SVG با بازه‌ی دلخواه (۷ تا ۳۶۵ روز)، پرفروش‌ترین کالاها، بهترین مشتری‌ها، سهم دسته‌بندی‌ها و گزارش ماه‌به‌ماهِ شمسی با خروجی CSV و چاپ
- **تنظیمات** — هزینه ارسال، بنر جشنواره، تعطیلی موقت فروشگاه
- **رویدادها** — تایم‌لاین کاملِ کارهای انجام‌شده با برچسبِ فارسی هر کنش و لحنِ رنگی (از جمله «سوختن کد ورود با پیامک» که قرمز نشان داده می‌شود)
- **خطاها** — خطاهای گروه‌بندی‌شده‌ی ۱۴ روزِ اخیر با تکرار، فاصله‌ی زمانی و stack trace
- **وضعیت سیستم** — متریک سرور، سلامت دیتابیس با بررسیِ عمیقِ درخواستی، فهرستِ بکاپ‌ها با دکمه‌ی «بکاپ فوری»، نمودار خطای ۷ روزِ اخیر و رویدادهای پنل

> منبعِ حقیقتِ فهرست `next-frontend/src/lib/adminSections.ts` است و نوارِ ناوبری و پانویسِ پوسته **هر دو** از همان ساخته می‌شوند، پس امکانِ واگرا شدن ندارند. حالا هیچ `href: null`ـی نمانده، پس نه برچسبِ «Express» در نوار است و نه پانویسِ وضعیتِ مهاجرت — آن دو شرطی بودند و خودشان ناپدید شدند. مجوزِ واقعیِ ادمین سمتِ Express اعمال می‌شود (`middleware.ts` در Next فقط «واردشده بودن» را چک می‌کند) و پوسته بر اساسِ همان تصمیم، نوار را برای کارمند و مشتری محدود می‌کند.

### سئو
- متاهای og/twitter و canonical **سمت سرور** تزریق می‌شوند
- JSON-LD: Store + WebSite + FAQPage + **ItemList محصولات پرفروش** (سرور-ساید)
- محصولات: Product + Offer + AggregateRating + BreadcrumbList
- sitemap.xml داینامیک با lastmod واقعی — نشانی‌های تمیز؛ نام‌های `.html` بازنشسته با ۳۰۱ دائمی به همین‌ها می‌رسند
- robots.txt داینامیک
- صفحه محصول حذف‌شده: در Express کد **۴۱۰** واقعی می‌گیرد (نه soft-404). در Next این مسیر SSG است و کد همان **۲۰۰** می‌ماند، پس به‌جایش `robots: noindex` برمی‌گردد — تفاوتی عمدی که در `product/[id]/not-found.tsx` دلیلش نوشته شده
- **تست خودکار سئو (۸۵ تست)**: canonical، og:image، robots، JSON-LD، meta description، title، img alt، favicon

### امنیت
- CSP کامل (بدون `unsafe-inline`) + گزارش‌گیری
- HSTS روی HTTPS
- CSRF دو لایه (sameSite cookie + بررسی Origin)
- Rate-limit چندلایه (سراسری + نوشتن + اختصاصی)
- قفل حساب بعد از رمز غلط پیاپی
- ماسک‌کردن شماره موبایل در لاگ
- Gitleaks برای جلوگیری از لو رفتن secretها
- **اسکن خودکار OWASP Top 10 (۴۷ تست)** روی ۱۰ دستهٔ آسیب‌پذیری
- **تست امنیت آپلود، CSRF، rate-limit (۴۵ تست)**
- **security.txt** برای responsible disclosure (RFC 9116)
- **HTTPS-GUIDE.md** — راهنمای کامل فعال‌سازی SSL، استقرارِ دوبرنامه‌ای (Express + Next)، تنظیمِ `CSRF_EXTRA_ORIGINS` و هدرهای امنیتیِ هر دو

### عملکرد
- **Cluster Mode**: استفاده از تمام هسته‌های CPU (روی لینوکس)
- **کش درون‌حافظه**: TTL ۲-۱۰ ثانیه برای queryهای پرتکرار
- **Rate-limit SQLite**: مشترک بین cluster workers
- **کش مرورگر**: CSS/JS immutable یک‌ماهه، HTML no-cache — در Next هدرِ `immutable` روی `/_next/static` فقط در production می‌آید، چون سرورِ dev چانک‌ها را **بدونِ هش** سرو می‌کند و کشِ یک‌ساله یعنی ویرایش‌های تو دیده نمی‌شوند
- **فشرده‌سازی**: gzip/brotli برای CSS/JS/SVG — کشِ محتوا‌محور، ETag هم از محتوا
- **WebP خودکار**: تحویل نسخه سبک‌تر اگر مرورگر بپذیرد
- **SQLite WAL**: خواندن و نوشتن هم‌زمان

## مجموعه تست‌ها

دوازده مجموعه‌ی شمارش‌پذیرِ بک‌اند + یک مجموعه‌ی فرانت‌اند + سه نگهبانِ بی‌شمارش:
نگهبانِ مرزِ راز (یا سبز است یا throw می‌کند)، هارنسِ تخریبیِ خودِ نگهبان‌ها
(`guard-mutations.js`) و
نگهبانِ مرزِ پنج‌تلاشِ کدِ پیامکی (`otp-attempt-cap.js`). مجموعه‌های
بک‌اند عمداً جدا مانده‌اند، چون هر کدام سرور را با سقف‌های نرخِ متفاوتی بالا
می‌آورد (تستِ دود سقف را باز می‌خواهد، تستِ امنیت و OWASP بسته) و قاطی‌کردنشان در
یک پروسه یعنی یکی سهمیه‌ی دیگری را می‌سوزاند.

```bash
cd backend

npm test                              # ۶۵۷ تست دود (test-smoke.js)
node tests/owasp-scan.js              # ۴۷ تست OWASP Top 10
node tests/security.js                # ۴۵ تست امنیت (آپلود، CSRF، جعل IP، rate-limit)
node tests/discount.js                # ۳۱ تست کد تخفیف و قیمت قبلی
node tests/bench-report-integrity.js  # ۱۸ تست یکپارچگیِ گزارشِ بنچمارک
node tests/order-window-integrity.js # ۱۴ تست همترازیِ پنجره‌ی صبر با مهلت و تیکِ بک‌اند
node tests/otp-resend-window.js    # ۸۷ بررسیِ ثانیه‌شمارِ ارسال مجدد: Nextِ زنده + اوراکلِ منجمدِ Express (ایستا + سرورِ سندباکس)
node tests/service-worker-strategy.js # ۲۲ بررسیِ استراتژیِ سرویس‌ورکر: صفحه‌ی برگشته‌ها تازه، تازه‌سازیِ پس‌زمینه، پشتیبانِ آفلاین
node tests/static-compress-cache.js # ۵۰ بررسیِ کشِ فشرده‌سازی: بایتِ تازه با همان mtime و اندازه هم دیده می‌شود
node tests/event-labels.js          # ۱۷ بررسیِ دفتر رویدادها: هر رویدادِ بک‌اند برچسبِ فارسی دارد
node tests/otp-attempt-cap.js          # مرزِ پنج‌تاییِ کدِ پیامکی، پیامِ «چند تلاش مانده»، و ردِ امنیتیِ سوختن (ایستا + سرورِ سندباکس)
node tests/panel-retired.js            # ۵ بررسیِ «پنلِ حذف‌شده برنگشته» + نبودِ ریشهٔ frontend/ — فقط خواندنِ سورس
node tests/readme-counts.js            # ۴۵ بررسیِ راستیِ عددهای README — بدونِ سرور
node tests/guard-mutations.js          # هارنسِ تخریبیِ نگهبان‌ها — خودِ نگهبان‌ها را با شکستِ عمدی می‌آزماید
```

```bash
cd next-frontend

npm run test:readme-counts # عددهای README را با نتیجه‌ی واقعیِ اجرا می‌سنجد (خودش vitest را اجرا می‌کند)
```

مقایسهٔ زنده‌ی فروشگاه (نیازمندِ هر دو سرور: Express روی ۳۰۰۰ و Next روی ۳۰۰۱):

```bash
cd next-frontend
npm run parity:storefront            # هر صفحهٔ Express را با همتای Next می‌سنجد — هر واگراییِ اعلام‌نشده قرمز می‌کند
npm run parity:storefront -- --report   # فقط گزارش، بدونِ شکست (کدِ خروج همیشه صفر)
npm run legacy-links:live            # مقصدِ نشانی‌های قدیمی (.html) و پوششِ نام‌ها — Next لازم است
npm run legacy-links:live -- --express=http://127.0.0.1:3000   # سمتِ Express هم سنجیده شود
npm run freeze:oracle                # اوراکل را بازمی‌سازد؛ امروز دیگر سرورِ Express آن صفحه‌ها را ندارد، پس صریح می‌ایستد و راهِ `git show` را نشان می‌دهد
npm run cutover:rehearsal            # تمرینِ کاتاور: هر دو دنیا روی یک پورت + خزش و فهرستِ شکست‌ها
npm run cutover:rehearsal -- --serve # فقط همان دامنهٔ واحد را بالا نگه دار (بدونِ خزش)
```

> میانِ این ۳۱۰ آزمون، هشت‌تای نخستِ صفحه‌ی نتیجه‌ی سفارش تنها چیزی در پروژه‌اند که
> رفتارِ **زمان‌محور** را می‌سنجند: ریتمِ ۱۵/۶۰ ثانیه‌ای و سقفِ ۴۷ بررسیِ همان صفحه را. نه typecheck می‌فهمد اگر آن
> اعداد عوض شوند و نه lint — و شکستنِ این حلقه یعنی مشتریِ پول‌داده تا ابد منتظر
> مانده یا سرور بی‌دلیل درخواست می‌گیرد. با تایمرِ جعلی همان اعدادِ production
> سنجیده می‌شوند، پس پنجره‌ی ۴۱ دقیقه‌ای در چند میلی‌ثانیه اجرا می‌شود و کدِ اصلی
> برای آزمون‌پذیر‌شدن حتی یک خط هم دست‌کاری نشده. هر مرزِ شبکه‌ای (`getOrder`،
> `getMe` و مسیریابِ Next) در خودِ آزمون جعل می‌شود.
>
> پوشش: بازیابیِ دیرهنگام (pending → paid)، شکستِ قطعی (canceled/failed)، پنجره‌ی
> صبر و توقفِ سرِ سقف، خطای گذرای شبکه، تبِ پنهان و بازگشتِ مشتری، و پاک‌سازیِ
> تایمر در unmount — به‌علاوهی درِ ورود و برگشتِ مشتری به همان سفارش، تفکیکِ
> ۴۰۴ از هر خطای دیگری، و سفارشِ دوباره با کالاهای ناموجود (با دلیلش).
>
> پنجره‌ی صبر خودش هم آزمون دارد، چون تا امروز با شمردنِ بررسی‌های همین صفحه
> اندازه گرفته می‌شد و یک F5 سقفش را دور می‌زد: حالا آغازِ پنجره در
> `localStorage` می‌ماند (به‌ازای هر سفارش) و تازه‌کردنِ صفحه یعنی ادامه از
> همان‌جا، غیبتِ طولانی با سیلِ درخواست جبران نمی‌شود، و پنجره سرِ همان ۴۱
> دقیقه‌ی آغازین تمام می‌شود.

میان‌بُرهای npm:

```bash
npm run test:all     # دود + امنیت + تخفیف  (test-all.js)
npm run owasp        # همان tests/owasp-scan.js
npm run test:full    # هر دوازده مجموعه‌ی بک‌اند + نگهبانِ راز — ۱۰۳۸ تست (بی بنچمارک)
npm run test:readme  # عددهای README در برابر خودِ کد (بدونِ سرور)
npm run test:resend  # ثانیه‌شمارِ ارسال مجدد در هر دو فرانت‌اند
npm run check        # test:all + سئو + بنچمارکِ ۲۰۰ کاربر  (بدونِ OWASP و راز)
```

> `npm run check` نامش قدیمی است و **همه‌ی** تست‌ها را اجرا نمی‌کند: بنچمارک دارد
> ولی OWASP و نگهبانِ راز را ندارد. برای پوششِ کامل `npm run test:full`، و اگر
> بنچمارک هم می‌خواهی هر دو را پشت سر هم.
>
> دو نگهبانِ سبکِ تازه‌تر داخلِ `test:full` نیستند چون هر کدام کارِ خودشان را
> دارند: `tests/otp-attempt-cap.js` (سرورِ سندباکسِ خودش) و
> `tests/guard-mutations.js` (فایل‌ها را عمداً خراب می‌کند و برمی‌گرداند —
> بی‌معنی است که کنارِ بقیه اجرا شود). هر دو در CI stepِ مستقل دارند.

> همهٔ این سنجش‌ها یک دروازهٔ واحد دارند: `node verify-before-commit.mjs` در ریشهٔ
> مخزن. حالتِ پیش‌فرض هر دو نگهبانِ عدد را به‌علاوهٔ جهش‌های بک‌اند و فرانت‌اند
> اجرا می‌کند، `--fast` فقط همان دو نگهبانِ عدد را در چند ثانیه می‌گیرد، `--live`
> سنجشِ زنده را هم اضافه می‌کند (هر دو سرور لازم است)، و `--install-hook` همین را
> به‌عنوانِ هوکِ pre-commit نصب می‌کند (هوکِ موجود را پاک نمی‌کند و `git commit
> --no-verify` راهِ دور زدنش است). سرِ اولین شکست می‌ایستد و دلیلش را می‌آورد،
> چون هدفش این است که «عددِ بیات» سرِ کامیت معلوم شود، نه موقعِ بازبینی.

همه‌ی مجموعه‌های بک‌اند روی **کپیِ** دیتابیس اجرا می‌شوند (`tests/sandbox.js` در پوشه‌ی
موقتِ سیستم)، پس هیچ‌کدام به داده‌ی واقعیِ مغازه دست نمی‌زند. تنها استثنا سه مجموعه است که هیچ دیتابیسی نمی‌خواهند و فقط سورس را می‌خوانند: بازنشستگیِ پنل، همترازیِ پنجره‌ی صبر، و راستیِ عددهای README. (ثانیه‌شمارِ ارسال مجدد دیگر یکی از همین‌ها نیست: نیمه‌ی زنده‌اش سرورِ سندباکسِ خودش را بالا می‌آورد — همان الگوی «مرزِ پنج‌تلاشِ کدِ پیامکی» — و روی همان کپی اجرا می‌شود.) مجموعه‌ی فرانت‌اند هم به سرور وصل نمی‌شود.

عددِ هر مجموعه **روی هر ماشینی یکی است**، چون هیچ سناریویی به «اگر فلان ردیف در
دیتابیس بود» گره نمی‌خورد: داده‌ی لازم هر کدام را خودِ آزمون می‌سازد و آخرِ کار پاک
می‌کند. تا پیش از این، بررسی‌های «پیش‌نویسِ محصول» فقط روی ماشینی اجرا می‌شد که ۸۸
پیش‌نویسِ `seed-catalog` را داشت؛ روی کلونِ تازه با دیتابیسِ تازه‌متولدشده‌ی
`seed.js` سه بررسی بی‌صدا رد می‌شد و CI عددِ کمتری را «همه سبز» می‌گفت (۷۳۲ در
برابر ۷۳۵). آن شکاف بسته شد: ماشینِ توسعه‌دهنده و کلونِ تازه هر دو ۷۴۶ می‌دهند.

## بازنشستگیِ فروشگاهِ Express — چه چیزی رفت، کجا رفت

پوشهٔ `frontend/` — همان فروشگاهِ vanilla با صفحه‌های `.html`، `js/`، `css/`،
سرویس‌ورکر و دارایی‌ها — حذف شد. دو چیز جایش را گرفت: **پلِ ۳۰۱** برای نام‌های
قدیمی (تا هیچ بوکمارک و هیچ نتیجهٔ گوگلی ۴۰۴ نشود) و **اوراکلِ منجمد**
(`next-frontend/tests/fixtures/legacy-src/` و `legacy-oracle/`) که مرجعِ
سنجشِ برابری است، چون از این پس «همان چیزی که Express می‌داد» روی دیسک نیست.

## یکپارچگیِ پیوسته (CI)

`.github/workflows/ci.yml` روی هر push و هر pull request اجرا می‌شود و همان کاری را
می‌کند که خودت دستی می‌کنی:

- **بک‌اند** — هر دوازده مجموعه به‌عنوانِ یک stepِ جدا (تا شکست، نامِ مجموعه را بگوید نه
  یک لاگِ چند‌هزارخطی)، به‌علاوه‌ی سه نگهبانِ بی‌شمارش (راز، مرزِ پنج‌تلاشِ کدِ
  پیامکی، و هارنسِ تخریبیِ خودِ نگهبان‌ها) — روی **Node ۲۲ و ۲۴** با `fail-fast: false`.
  ماتریس عمدی است: `engines` می‌گوید `>=22.5` ولی توسعه روی ۲۴ انجام می‌شود، و
  تفاوتِ نسخه‌ها دقیقاً چیزی است که دیر معلوم می‌شود.
- **فرانت‌اند** — `typecheck`، `lint`، `test`، `test:readme-counts`، هارنسِ تخریبیِ
  نگهبان‌های فرانت‌اند، و در آخر `build` **با بک‌اندِ زنده**، و بعد دو سنجشِ زنده:
  `static-paths:live` (با Nextِ تنها، بدونِ بک‌اند)، برابریِ فروشگاه به‌علاوه‌ی جهش‌هایش
  (با هر دو سرور)، و بازنشستگیِ نشانی‌های قدیمی روی Nextِ زنده
  (`legacy-links:live --express=http://127.0.0.1:3000`) — همه در بولت‌های پایین‌تر باز شده‌اند.
- **دو طرفِ یک مهلت** — نگهبانِ تازه‌ای (`tests/otp-resend-window.js`) همان قراردادِ
  «ثانیه‌شمارِ ارسال مجدد» را در **دو فرانت‌اند** قفل می‌کند: فروشگاهِ Express و درگاهِ
  ورودِ Next. هر دو باید «لحظه‌ی پایان» را ذخیره کنند و هر تیک را از همان لحظه
  بازمحاسبه کنند — نه با شمارنده‌ی کاهنده‌ای که پشتِ تبِ مخفی یا لپ‌تاپِ خواب‌رفته از
  واقعیت عقب می‌ماند. عبارت‌های هر دو طرف از سورس برداشته و با ساعتِ جعلی **اجرا**
  می‌شوند، چون یک `*` به‌جای `/` هم می‌تواند آزمونِ الگو-محور را سبز نگه دارد.
  خودِ عددِ مهلت هم از سرور می‌آید (`retryAfter`): در ارسالِ موفق مهلتِ کامل و در
  پاسخِ «کدِ قبلی هنوز معتبر است» مهلتِ باقی‌مانده — که کوتاه‌تر است، پس فرانت خودش
  را کوتاه می‌کند تا عددی که کاربر می‌شمارد با عددی که سرور اعمال می‌کند یکی باشد.
  و یک نیمه‌ی **زنده** هم دارد: سرورِ سندباکس با دیتابیسِ یک‌بارمصرف بالا می‌آید،
  درخواستِ اول کد می‌زند و بعد از گذشتنِ بخشی از پنجره درخواستِ دوم — ۴۲۹ باید همان
  باقی‌مانده‌ی واقعی را بدهد (از مُهرِ `last_sent_at` خودِ دیسک بازسازی می‌شود)، و
  همان عدد داخلِ قالبِ برچسبِ دکمه‌ی هر دو فرانت اجرا می‌شود تا معلوم شود عددی که
  کاربر روی صفحه می‌بیند همان عددی است که سرور اعمال می‌کند.

  **اوراکلِ منجمد** — با بازنشستگی، نیمهٔ Expressی مقایسه زنده از دست می‌رفت:
  `frontend/` حذف شد و «همان چیزی که Express می‌داد» دیگر مرجعی نداشت. پس

  (`next-frontend/scripts/freeze-legacy-oracle.mjs`) همین آرشیو را بازمی‌سازد و
  جزئیاتِ هر صفحه (کدِ وضعیت، اندازه، هش، منبع) را چاپ می‌کند. سه قفل دارد تا
  اوراکل به‌دستِ خودش خراب نشود: فایلِ موجود را بی`--force` بازنویسی نمی‌کند،
  پاسخی که ۲۰۰ نیست را منجمد نمی‌کند (یعنی پس از روشن‌شدنِ بازنشستگی، `--force`
  هم چیزی خراب نمی‌کند و با راهنمایِ «از `git show HEAD:frontend/…` بگیر» می‌ایستد)،
  و پاسخِ غیرِHTML را هم رد می‌کند. `--no-oracle` هم عمداً هست تا بتوان دو حالت را
  کنارِ هم سنجید (A/B): همان کاری که نشان می‌دهد انجماد رفتارِ نگهبان را عوض
  نکرده است. کدِ وضعیت همچنان *زنده* سنجیده می‌شود؛ فقط بدنه منجمد است.
  **در CI این اجراکننده در حالتِ پاک هم بالا می‌آید**:
  هر push و هر pull request، با هر دو سرورِ زنده، اگر یک واگراییِ اعلام‌نشده
  اضافه کرده باشد همان‌جا قرمز می‌شود — نه فقط زیرِ جهشِ هارنس (که اثباتِ
  «می‌گیرد» است، نه سنجشِ خودِ درخت). یک هشدارِ راه‌اندازی: canonical/og:url از
  `SITE_URL` (Express) و `NEXT_PUBLIC_SITE_URL` (Next) می‌آید؛ اگر این دو یکی
  نباشند، هر صفحه «واگراییِ تازه» می‌دهد. CI برای همین `SITE_URL` را روی همان
  پیش‌فرضِ Next (`http://localhost:3001`) می‌گذارد — همان مقداری که `backend/.env`
  روی ماشینِ توسعه دارد.

  بوکمارک و هر لینکِ دست‌به‌دست‌شده می‌شکست — بدترینش برگشتِ درگاهِ پرداخت به

  (`next-frontend/scripts/legacy-links-live.mjs`) برای هر نگاشتِ

  دقیق (کوئری و `?next=`→`?redirect=`) **و** اینکه گامِ آخر ۲۰۰ باشد، نه ۴۰۴/۴۱۰.

  است: در حالتِ گذار ۲۰۰ می‌دهد و به‌صورتِ «بدهیِ باز» شمرده و چاپ می‌شود؛ پس از
  ریدایرکت باید به **همان مقصدِ Next** برود و ۴۰۴ در هر دو حالت تخلف است — یعنی
  این نگهبان خودش گامِ بعدیِ بازنشستگی را می‌سنجد، نه فقط وضعِ امروز را. دو حالتِ
  لبِ مرز را هم از خودش جدا می‌کند: نبودنِ پوستهٔ قدیمی روی دیسک «بازنشسته» است

- **کشِ فشرده‌سازی با محتوا تازه شود، نه با timestamp یا هشِ ۳۲ بیتی** — سرورِ Express دارایی‌های CSS/JS را
  فشرده و در حافظه کش می‌کند و کلیدِ آن کش `(mtimeMs, size)` بود. یعنی تغییرِ بایتی که `mtime`
  و اندازه را دست نمی‌زد (restore از بکاپ با حفظِ timestamp، `cp -p`، یا ادیتی که در همان
  میلی‌ثانیه بنشیند) بدنهٔ کهنه را سرو می‌کرد: `200` می‌داد و `Content-Length` هم درست بود، ولی
  بایت‌ها مالِ قبل بودند. هیچ‌کدام از آن دو عدد توصیفِ محتوا نیستند؛ `mtime` را ابزارِ بکاپ
  می‌تواند عمداً برگرداند و `size` با یک جایگزینیِ هم‌اندازه ثابت می‌ماند. حالا فایل در هر
  درخواست خوانده می‌شود و ۶۴ بیتِ اولِ `sha1` محتوا اعتبارِ کش را تعیین می‌کند (هزینه‌اش ~۰٫۱۵
  میلی‌ثانیه برای style.css (~۱۷۰ کیلوبایت)، در برابر ~۳٫۸ میلی‌ثانیه فشرده‌سازیِ brotli که همچنان کش می‌شود)، و
  `ETag` هم از همان هش ساخته می‌شود — وگرنه مرورگری که `ETag`ِ قدیمی را داشت `304` می‌گرفت و
  بدنه‌ی کهنه‌اش را نگه می‌داشت و باگ از سمتِ کلاینت برمی‌گشت. نگهبانِ
  `tests/static-compress-cache.js` خودِ میان‌افزار را با فایلِ موقتِ واقعی اجرا می‌کند، بایت را
  با `mtime` و اندازه‌ی *ثابت* عوض می‌کند و بدنه‌ی سروشده را پس از بازکردن با دیسک مقایسه
  می‌کند (۵۰ بررسی) — به‌علاوهٔ این‌که بارِ دومِ همان محتوا واقعاً از کش می‌آید، یعنی رفعِ باگ
  کش را بی‌اثر نکرده.
  همین دسته‌باگ در کشِ **HTML** هم بود، ولی از سمتِ اثرِ انگشت: `sendHtml` کلیدش را از
  `${encoding}|${buf0.length}|${hash32(html)}` می‌گرفت و آن `hash32` یک FNV-1a ۳۲ بیتی بود.
  نکته‌ی ظریف این که FNV-1a روی ورودی‌های *هم‌طول* یک‌به‌یک است (هر گام XOR و ضرب در عددی
  فرد است، پس برگشت‌پذیر)، یعنی دو رشته‌ی هم‌تعداد-واحدِ کد هرگز تصادم نمی‌کنند؛ ولی کلیدِ
  قدیمی طولِ **بایتِ UTF-8** را می‌سنجید و هش را روی **واحدهای کدِ UTF-16** می‌گرفت. شکاف
  دقیقاً همین ناهم‌خوانی است: چهار نویسه‌ی فارسی و هشت نویسه‌ی ASCII هر دو ۸ بایت‌اند ولی ۴ و
  ۸ واحدِ کد — پس دو سندِ کاملاً متفاوت می‌توانستند یک کلید بگیرند و کش بی‌سروصدا سندِ
  جابه‌جا سرو کند: `200`، `Content-Length` درست، بایت‌ها مالِ صفحه‌ی دیگر. حالا HTML هم همان
  ۶۴ بیتِ اولِ `sha1` را هویتِ کش می‌گیرد (یک هویتِ محتواییِ مشترک با فایل‌های استاتیک)، و
  نگهبان در زمانِ اجرا خودش یک جفتِ تصادم‌دارِ ۳۲ بیتی می‌سازد و نشان می‌دهد بدنه از محتوا
  پیروی می‌کند نه از آن کلیدِ کم‌عرض — و هم‌زمان این که کشِ HTML همچنان کش است: سندِ دوم
  دوباره فشرده می‌شود و بارِ سومِ سندِ اول از کش می‌آید.
- **صفحه‌ی کاربرِ برگشته هرگز کهنه نباشد** — سرویس‌ورکر تنها کدی است که *بینِ* کاربر و
  سرور می‌نشیند و می‌تواند بی‌هیچ خطای سروری نسخه‌ی کهنه را نشان دهد، ولی تا امروز کسی
  این تصمیم را نمی‌سنجید. حالا ناوبری همیشه `cache: 'no-cache'` می‌رود (یعنی حتی اگر
  مرورگر یا واسطه‌ای خیال کند صفحه تازه است، باز از سرور می‌پرسد)، همان HTMLِ سالم در
  پس‌زمینه کپی می‌شود تا کپی هیچ‌وقت از یک ناوبری کهنه‌تر نباشد، و کش فقط وقتی به کار
  می‌آید که شبکه *نباشد* — آن‌جا هم اول صفحه‌ی خودش، بعد صفحه‌ی آفلاین. نگهبانِ
  `tests/service-worker-strategy.js` این‌ها را **اجرا** می‌کند (شبکه و کشِ جعلی) و
  یکسان‌بودنِ دو کپیِ سرویس‌ورکر در دو برنامه را هم می‌سنجد، وگرنه دو فروشگاه دو رفتارِ
  متفاوت به کاربر می‌دهند.
- **کلیدِ خام در دفترِ رویدادها نماند** — هر رویدادی که در بک‌اند ثبت می‌شود باید
  برچسبِ فارسی داشته باشد، وگرنه مدیر در `/admin/activity` کلیدِ ماشینی می‌بیند. یک‌بار
  همین اتفاق افتاد: از میانِ کلیدهای آن روز، همه‌ی CRM و عمده‌فروشی ترجمه نشده بودند و
  چون هیچ‌چیز دو فهرست را به هم گره نزده بود، کسی نفهمید. نگهبانِ
  `tests/event-labels.js` کلیدها را از خودِ فراخوانی‌های `note(…)` و `logAdminAction(…)`
  بیرون می‌کشد، با نقشه‌ی پنل مقایسه می‌کند، و جهتِ برعکس را هم می‌گیرد: برچسبی که رویدادی
  پشتش نیست «بی‌صاحب» است و کلیدِ تغییرنام‌داده را لو می‌دهد. مجموعش (۱۷ بررسی)
  نه سرور می‌خواهد نه دیتابیس.
- **حذف نباید برگردد** — نگهبانِ سبکِ دیگری (`tests/panel-retired.js`) فقط دیسک را
  می‌خواند: اگر فایلِ پنلِ حذف‌شده دوباره سرِ جایش بگذارند یا کسی دوباره به آن
  ارجاع بدهد (حتی به شکلِ regex یا مسیرِ ویندوزی)، قرمز می‌شود. ۴۰۴ بودنِ زنده‌ی
  همان مسیرها هم در همان مجموعه‌ی دود سنجیده می‌شود — یکی سورس، یکی خودِ سرور.
- **خودِ نگهبان‌ها هم آزمون دارند** — `tests/guard-mutations.js` یک هارنسِ
  تخریبی است: برای هر نگهبان چند خرابیِ عمدی می‌سازد، فایل را بایت‌به‌بایت در
  حافظه نسخه می‌گیرد، نگهبان را اجرا می‌کند و اگر قرمز نشد (یا دلیلِ درست را
  نگفت) همان‌جا شکست می‌خورد؛ بعد فایل را برمی‌گرداند و با هشِ SHA-256 تأیید
  می‌کند که مو‌به‌مو همان چیزی است که بود. دامنه‌ها: `--scope=backend` (نگهبان‌های بک‌اند؛ دو تایشان — مرزِ پنج‌تلاشِ کدِ پیامکی و پنجره‌ی ارسال مجدد — سرورِ سندباکسِ خودشان را بالا می‌آورند)، `--scope=frontend` (نگهبان‌های Vitest و اسکریپتِ عددهای README)،
  `--scope=live` (اجراکننده‌ی زنده‌ی برابری، با هر دو سرور بالا). در CI هر سه
  اجرا می‌شوند: نگهبانی که هیچ نمی‌گیرد، از نبودنش بدتر است.

چرا بک‌اند در jobِ فرانت‌اند بالا می‌آید: `product/[id]/page.tsx` محصولات را در
زمانِ بیلد پیش‌رندر می‌کند و خطاهای API عمداً قورت داده می‌شوند — پس یک بیلدِ سبزِ
**توخالی** با صفر صفحه‌ی محصول ممکن است. بعد از بیلد تعدادِ HTMLهای محصول شمرده
می‌شود و اگر صفر باشد، اجرا قرمز می‌شود.

روی یک checkout تازه که `backend/data` ندارد، سرور تست دیتابیس را از صفر می‌سازد و
`lib/seed.js` محصولات را می‌کارد؛ پس CI به هیچ داده‌ی از پیش موجودی وابسته نیست.
نشان‌های بالای همین صفحه وضعیتِ واقعیِ همین workflowها هستند، نه یک بجِ دستی.

## بنچمارک

```bash
cd backend

# تست کامل (۴۰۰ خریدار + ۴۰۰ خواننده)
bash bench-report.sh

# فقط نوشتن
bash bench-report.sh write 1500

# فقط خواندن
bash bench-report.sh read 5000

# اجرای مستقیم
node bench-load.js 400               # بنچمارک نوشتن
node bench-read.js 400               # بنچمارک خواندن
```

`bench-report.sh` خروجی را تجزیه می‌کند و به‌صورت بلوک new در `benchmark-report.md` ذخیره می‌کند (append — محتوای قبلی پاک نمی‌شود).

> منبعِ حقیقتِ مسیرش `backend/lib/paths.js` است و سرور آن را روی `/picture`
> سرو می‌کند.
>
> نکته‌ی گرانی که یک بار تجربه شد: هر عکسی که یک **صفحه‌ی ثابت** به آن ارجاع می‌دهد
> باید در همین مخزن باشد، نه فقط روی دیسکِ کسی که آن را ساخته. لوگو یک بار با پسوند
> `.jfif` بود و `.gitignore` همان پسوند را نادیده می‌گرفت؛ نتیجه: همه‌ی بررسی‌های
> «فایل هست؟» سبز بودند و سایت روی کلونِ تازه بدونِ لوگو بالا می‌آمد. حالا عکس‌ها
> همان شکلِ عکس‌های محصول را دارند (`.jpg` اصلی به‌همراهِ `.webp` و `-320w.webp`، همه
> ترک‌شده) و `V24` در مجموعه‌ی دود هم می‌سنجد که هر ارجاعِ ایستا **در گیت** باشد، نه
> فقط روی دیسک. این سنجش به `<img>`های HTML و `/picture/` محدود نمی‌ماند: `url()`
> در CSS، آیکون‌های `manifest.webmanifest` و فهرستِ precacheِ سرویس‌ورکر هم پوشش
> داده می‌شوند — یک قلمِ precacheِ گمشده روی کلونِ تازه نصبِ PWA را می‌شکند بی‌آنکه
> لاگِ سرور چیزی بگوید. کامنت‌ها قبل از اسکن حذف می‌شوند تا یادداشتِ تاریخیِ
> «مسیری که دیگر نیست» نگهبان را الکی قرمز نکند.

## مسیر خرید

۱. مشتری محصول رو به سبد اضافه می‌کنه (بدون نیاز به ورود)
۲. وارد صفحه‌ی سبد خرید می‌شه، تعداد رو تنظیم می‌کنه (یا آیتم حذف‌شده را بازگردانی می‌کنه)
۳. روی «تکمیل خرید» می‌زنه → اگه وارد نشده، به صفحه‌ی ورود می‌ره
۴. با شماره موبایل، کد ۵ رقمی دریافت می‌کنه و وارد می‌شه
۵. آدرس تحویل رو وارد می‌کنه (یا از آدرس‌های قبلی انتخاب می‌کنه)
۶. روی «پرداخت» می‌زنه → به درگاه زرین‌پال منتقل می‌شه
۷. بعد از پرداخت، سفارش ثبت می‌مونه و مشتری فاکتور می‌بینه
۸. اگر تأییدیه‌ی درگاه هنوز نرسیده باشه، همین صفحه خودش هر ۱۵ ثانیه (و بعد هر ۱ دقیقه) از سرور می‌پرسه، تا سقفِ ۴۱ دقیقه — بی‌اینکه مشتری کاری بکنه یا صفحه رو دوباره باز کنه. هر وقت نتیجه روشن شد، کارت و پیامِ بالای صفحه خودشون عوض می‌شن و یک پیامِ تأیید می‌ده.

## تنظیمات محیطی

```env
NODE_ENV=production
SESSION_SECRET=<حداقل ۳۲ کاراکتر تصادفی>
COOKIE_SECURE=true
ADMIN_PHONE=<شماره موبایل مدیر — ۰۹xxxxxxxxx>
SITE_URL=https://your-domain.com
```

> `ADMIN_PHONE` عمداً نمونه‌ی واقعی ندارد. ورود مدیر با پیامک به همین شماره
> انجام می‌شود، پس نوشتنِ عددِ واقعی در مخزنِ عمومی یعنی اعلامِ اینکه کلیدِ
> پنل دستِ کدام شماره است. مقدارش فقط در `.env` روی سرور بماند.

سرویس‌های اختیاری:
- `ZARINPAL_MERCHANT_ID` — درگاه پرداخت واقعی
- `SMS_API_KEY` — ارسال پیامک واقعی
- `BACKUP_DIR2` — بکاپ خارج از دیسک اصلی
- `CLUSTER_ENABLED=true` — حالت cluster (فقط لینوکس)

فرانت‌اند Next.js (`next-frontend/.env.example`):

```env
API_ORIGIN=http://localhost:3000            # مبدأِ Express برای SSR/SSG/Server Actions
NEXT_PUBLIC_SITE_URL=http://localhost:3001  # پایه‌ی canonical، sitemap، robots و JSON-LD
```

> دو نکته که اگر رعایت نشوند فرانت‌اند نیمه‌کاره بالا می‌آید. اول: `API_ORIGIN`
> عمداً `NEXT_PUBLIC_` نیست — مرورگر باید مسیرِ **نسبی** بزند تا `rewrites` در
> `next.config.ts` آن را پروکسی کند؛ اگر مرورگر مستقیم به `:3000` بزند، درخواست
> cross-origin می‌شود و Express نه CORS می‌دهد نه کوکیِ نشست را می‌پذیرد. دوم: در
> `backend/.env` باید `CSRF_EXTRA_ORIGINS=http://localhost:3001` باشد، وگرنه هر
> «نوشتن» از Next با ۴۰۳ رد می‌شود، چون مرورگر `Origin` را با پورتِ ۳۰۰۱ می‌فرستد
> و Express آن را غریبه می‌بیند.

## انتشار (Deploy)

بک‌اند (Express) و فرانت‌اندِ Next هر کدام برنامه‌ی خودشان‌اند و در production پشتِ **یک دامنه** می‌نشینند: nginx (یا هر پروکسیِ دیگری) مسیرهای `/api` و `/picture` را به Express و بقیه را به Next می‌دهد — پیکربندیِ کامل در `HTTPS-GUIDE.md`. از عصرِ `frontend/` دیگر چیزی برای سروکردن لازم نیست؛ فقط نگاشتِ ۳۰۱ در `backend/lib/legacy-redirects.js` می‌ماند و متنِ منجمدِ صفحه‌ها در `next-frontend/tests/fixtures/legacy-oracle/` مرجعِ سنجشِ برابری است.

پوشه‌ی `backend/` روی هر سرویس Node.js:
- ایران: لیارا یا آروان‌کلود
- عمومی: Railway، Render، یا VPS

```bash
# با PM2:
CLUSTER_ENABLED=true pm2 start ecosystem.config.js

# یا مستقیم:
CLUSTER_ENABLED=true node backend/server.js
```

فرانت‌اند Next.js:
```bash
cd next-frontend
npm run build
npm start       # اجرا روی port 3001
```

> در production دو متغیرِ همین پوشه باید ست باشند: `API_ORIGIN` روی آدرسِ Express
> و `NEXT_PUBLIC_SITE_URL` روی دامنه‌ی واقعیِ https — پایه‌ی canonical، sitemap،
> robots و JSON-LD همین است، و اگر اشتباه باشد گوگل آدرس‌های لوکال را ایندکس
> می‌کند. و در `.env` بک‌اند، `CSRF_EXTRA_ORIGINS` باید دامنه‌ی فرانت‌اند را داشته
> باشد؛ در غیر این صورت ورود و ثبت سفارش روی سایتِ Next با **۴۰۳** رد می‌شود و
> پیامِ خطا هم دلیلش را نمی‌گوید.

## امنیت

### اسکن‌های خودکار
```bash
node tests/owasp-scan.js       # اسکن OWASP Top 10 (۴۷ تست)

```

`security.yml` در CI هر push را با Gitleaks اسکن می‌کند — وضعیتش در نشانِ بالای
همین صفحه دیده می‌شود.

### گزارشِ آسیب‌پذیری
اگر ایرادِ امنیتی پیدا کردید، لطفاً به‌صورت عمومی issue نسازید.
راهِ درستش در [SECURITY.md](SECURITY.md) نوشته شده. فایلِ RFC 9116 یک نسخه دارد
و همان هم کافی است: `next-frontend/public/.well-known/security.txt` که سایتِ
Next روی خودِ دامنه سرو می‌کند. نسخه‌ی دومِ عصرِ Express
(`frontend/.well-known/security.txt`) با حذفِ آن فروشگاه رفت؛ `Policy` آن نسخه
به `/terms.html` اشاره می‌کرد و امروز همان نشانی با ۳۰۱ به `/terms` می‌رسد.
ارجاع‌های فایلِ زنده با آزمونِ `internalLinks.test.ts` سنجیده می‌شوند تا
آدرسِ مرده‌ای در آن جا نماند.

### Gitleaks دستی

```bash
gitleaks detect --redact --config gitleaks.toml --source .
```

## ابزارهای مدیریتی

همه بدونِ هیچ پکیجِ بیرونی و همه با `cd backend` اجرا می‌شوند.

| ابزار | کار |
|---|---|
| `node tools/restore-backup.js` | فهرستِ بکاپ‌ها. بی‌آرگومان **هیچ چیزی را عوض نمی‌کند** — فقط نشان می‌دهد. بکاپِ نیمه‌کاره را قبل از اعتماد رد می‌کند. |
| `node tools/restore-backup.js 2026-08-20` | بازگردانی به آن روز — با عکسِ `pre-restore-*` و تأییدِ `yes` |
| `node tools/seed-catalog.js` | افزودنِ محصولاتِ **پیش‌نویس** (`published = 0`) — روی سایت دیده نمی‌شوند تا خودت عکس و قیمت بگذاری |
| `node tools/optimize-images.js` | ساختِ نسخه‌ی WebP کنارِ هر عکس (۲۵–۴۵٪ سبک‌تر) |
| `node tools/log-summary.js --days=7` | خلاصه‌ی خطاهای لاگ |
| `node tidy-test-data.js` | فهرستِ رسوبِ تست دود (سرور خاموش). با `--apply` پاک می‌کند؛ موجودی را **عمداً** دست نمی‌زند. |
| `node tidy-test-data.js --check-stock` | مقایسه‌ی موجودی با آخرین بکاپ |
