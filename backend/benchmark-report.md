## ۴. تحلیل

### گلوگاه اصلی: Event Loop Node.js

```
توان نوشتن:  ~1700-1800 req/s (ثابت از ۱۵۰۰ تا ۵۰۰۰ کاربر)
توان خواندن:  خطی رشد میکنه — ۱۰۰۰۰ نفر هنوز ۱۰۰٪ موفق
```

خواندن بسیار سبک‌تر از نوشته: در ۱۰,۰۰۰ خواننده همزمان، سریع‌ترین مسیر (جزئیات محصول) فقط p50=837ms و کُندترین (لیست) p50=2258ms هست — ولی **صفر خطا**.

### سقف پیشنهادی — نوشتن

| سطح | تعداد کاربر همزمان | توضیح |
|---|---|---|
| 🟢 بهینه | ≤ ۴۰۰ | p99 < ۲۵۰ms — تجربه عالی |
| 🟡 قابل قبول | ≤ ۱۵۰۰ | p99 < 1s — تجربه خوب |
| 🟠 کند ولی کارآمد | ≤ ۳۰۰۰ | p99 ~1.5s — تجربه قابل قبول |
| 🔴 آستانهٔ فروپاشی UX | ۵۰۰۰ | p99 > 2.5s — تجربه بد |

### سقف پیشنهادی — خواندن

| سطح | تعداد کاربر همزمان | توضیح |
|---|---|---|
| 🟢 بهینه | ≤ ۱۰۰۰ | p99 < 200ms — تجربه عالی |
| 🟡 قابل قبول | ≤ ۵۰۰۰ | p99 < 1.2s — تجربه خوب |
| 🟠 کند ولی کارآمد | ≤ ۱۰۰۰۰ | p99 < 2.3s — تجربه قابل قبول |

| متریک | مقدار |

## ۵. ملاحظات

- بنچمارک روی **Sandbox ایزوله** اجرا شده — دیتابیس واقعی آسیب نمی‌بینه.
- سقف نرخ (rate-limit) در تست ۱۵۰۰-۱۰۰۰۰ باز بوده (raw performance).
- تست ۴۰۰ نفر با **سقفهای واقعی** (CGNAT view) اجرا شده.
- CPU Benchmark خاص هست — Real-world latency ممکنه ۱۰-۲۰٪ بهتر باشه (keep-alive, connection reuse).
